# 搜索结果治理机制（反推送）

> 项目令（2026-10-17）：**推送整治得形成搜索引擎的机制**——不是某个模式的临时补丁，而是每一次搜索都强制经过的一层。

## 为什么要有这一层

B站搜索有两层低相关内容：

1. **分词泛匹配**：长句被拆成片段乱命中（「キラキラだとか夢だとか」→ キラメキ、ダイキラ……）；
2. **纯推送位**（更狠）：接口 `hit_columns` 为空——连分词都没命中的推荐卡，被硬塞进结果占位。

实测（2026-10-17，`キラキラだとか夢だとか`）：page1 全词命中 34/50 → page6 只剩 14/50；纯推位 page1 6/50 → page6 26/50，越深越脏。

## 机制结构

- 代码：`src/usable_search/governance.py`
  - `RULES` 规则表（增删规则只改这里 ＋ `Governor.check` 的判定位）
  - `Governor`：单次搜索的治理器，逐条判定并计数
  - `log_run`：账本落库；`stats`：账本汇总
- 接线：`server.py` 的 `run_bilibili()` 在条目入池前逐条过 `gov.check(v)`；
  返回体带 `governance: {enabled, match, kept, dropped{...}, dropped_total, rules[]}`。
- 账本：`data/governance.sqlite3`（gitignore）——每次**实际抓取**落一行：
  `ts / source / q / mode / params / scanned / kept / dropped(json)`。
- 查询：`GET /api/governance?q=<关键词>`（最近 30 次 ＋ 按规则合计）——B5 的定量核查与趋势观察直接读这里。

## 规则表（当前）

| id | 名称 | 判定 | 状态 |
|----|------|------|------|
| push | 纯推送位 | `hit_columns` 为空（连分词都没命中） | 开 |
| live | 直播内嵌卡 | `is_live_room_inline` 为真 | 开 |
| phrase | 全词命中 | 标题/简介/标签必含完整关键词（strict 仅标题） | 开（std/strict） |

## 口径

- **默认开**：`match=std`（标准）或 `strict`（严格）→ 治理生效；
- **宽松（`match` 空）＝治理整体关闭**：保留平台原样，作为对照口径（不是"关掉治理"的常态）；
- 治理计数永远展示在状态行：「匹配 N 条（已扫 M 条）· 治理剔除 K 条（推位 a · 直播 b · 非全词 c）」。

## 红线（治理边界）

- 治理层**只允许删除"非内容"**：零命中纯推位、直播内嵌卡等平台填充物；
- **真实命中搜索内容的一律不删**——包括软广、搬运、低质在内的"内容级问题"，最多只能在后期「智能搜索」模式里**降权/后排**；
- 理由：一旦按"软广"等理由删真内容，我们就成了另一个平台（"和叔叔阿姨没两样"）。
- 低质过滤（B6）同受此红线约束：只降权，不剔除。

## 多通道召回（v0.4.1）

问题现场（实测）：搜索「春廷雪」（故意错字）——**错字视频确实存在**，但站点综合排序的前 1000 条里 962 条是纯推位，真结果被淹没，标准档匹配 0。

探路结论（2026-10-17 实测）：
- `order=totalrank`（综合排序）通道：充满纯推送位（hit_columns 空），越深越多；
- `order=pubdate/click/dm/stow` 通道：**几乎没有纯推位**，且能捞到同一个词的不同结果集。

机制：`run_bilibili` 的主扫描抽成 `_scan(通道, 页数上限)`；主通道扫完后若结果数量凑不满一页（need = page×size），依序补充
`pubdate → click → dm → stow`（跳过已用通道，每条 ≤10 页，至多补 2 条），逐条过 Governor 后合并去重。
响应与账本带 `channels` 清单；状态行显示「通道 N」。

效果：春廷雪 → 匹配 2 条（懒小羊版《春廷雪》/好美#春廷雪），通道 3，23 秒；常规词（MyGO）单通道 0.6 秒，不触发补捞。
