## 二、可直接抄的四条

### 1. 多源失败隔离（来源：searxng）
searxng 对每个引擎单独设超时，一个引擎挂了不影响整体返回，只是少了那一路结果。
**我们的问题**：`src/usable_search/server.py` 的聚合分支用 `Promise.all`，B站风控会让已经成功的网易云结果一起消失。
**落法**：聚合改成「每源独立 try/catch + 各自超时」，单源失败在响应里带 `degraded: ["bilibili"]` 和原因，前端在状态行显示「B站暂不可用，仅显示网易云」。这条优先级最高，改动最小。

### 2. 错字容忍的代价预算（来源：typesense `art.cpp`）
typesense 不做全局编辑距离扫描，而是在前缀树上边走边扣代价（`max_cost`），超过预算就剪枝。
**我们的问题**：X3 模糊搜索如果对全表算编辑距离，几万条就顶不住。
**落法**：先取候选集（同首字 / 同拼音首字母 / 长度差 ≤1），再在候选集内算编辑距离，不做全表扫描。容量估算：候选集控制在 500 条内，单次 ≤20ms。

### 3. 字段权重与长度归一（来源：tantivy `fieldnorm` + `collector`）
tantivy 用字段长度归一化避免「长简介碰巧命中」压过「标题精准命中」。
**我们的问题**：`rank.py` 的 score 只看「精确/前缀/包含」，没考虑字段来源，也没考虑长度惩罚以外的信号。
**落法**：加分项按字段分档（标题 1000 / 标签 700 / 简介 500），再乘长度惩罚 `1/(1+log(len))`。改之前必须先跑 `tests/test_recall.py` 拿基线，改完 9 条不能掉。

### 4. 即时搜索的前缀索引（来源：meilisearch）
meilisearch 的 search-as-you-type 靠倒排索引+前缀，不靠 LIKE 全表扫。
**我们的问题**：现在每敲一个字都要重新请求平台，延迟全在平台上。
**落法**：本地索引（`songs` 表）先出结果垫底，平台结果回来再覆盖——「先快后准」。配合 E4 的 FTS5 trigram 一起做，不单独开工。

## 三、明确不抄的

- **不引入独立搜索服务**（meilisearch/typesense 二进制）：单机、单人用，多一个进程多一份运维和内存占用，性价比不成立。
- **不换技术栈**：不引入 Rust/C++ 组件，不为了性能重写 Python 层。
- **不用 BM25 替换现有排序**：现有排序是Owner定的业务规则（原唱去混淆、歌单置顶），BM25 只能做二次加权，不能当主排序。
- **不照抄 bilibili-API-collect**：仓库已关停，接口随时变，以实测为准。

## 四、落地优先级

1. **P0 聚合失败隔离**（searxng 思路）— 半天，直接改善「B站一风控整个页面空」的体验
2. **P1 歌词并发 + 连接复用**（性能，不依赖参考仓）— 半天，N1 从 5-10 秒降到 2 秒内
3. **P2 字段权重打分**（tantivy 思路）— 一天，须先有召回基线
4. **P3 X3 模糊搜索**（typesense 思路）— 两天起，候选集 + 编辑距离
5. **P4 即时搜索垫底**（meilisearch 思路）— 依赖 E4 FTS5，排其后
